# 請求書一括振込システム

請求書PDFをまとめて取り込み、内容を確認・承認したうえで、
**ドコモSMTBネット銀行の総合振込CSV（Shift_JIS）** を出力するツール。

「取り込み → 自動読み取り → 画面で確認・修正 → 承認 → CSVダウンロード」までと、
**取引先マスタによる不足項目の補完・口座変更の検知**、
**専用Gmailアドレスからの一括取り込み**まで実装済み。

**取り込み**タブの中に入口が2つあり、どちらも使えます。

| | 用途 |
|---|---|
| **メール経由**（`/upload`） | 請求書受け取り専用のGmailに届いた請求書を期間指定で一括取り込み。**PDFの添付**と**本文のリンク**の両方を見ます。月末の主作業 |
| **アップロード経由**（`/upload/file`） | 手元のPDFをドラッグ&ドロップ。Gmail以外の経路で届いたものや、1件だけ急ぎで入れたいとき |

本文のリンクは、**PDFに直接つながるものは取り込み**、**ログインが必要なもの（楽々明細など）は
「取引先にPDF送付を依頼する対象」として残します**。依頼メールを画面から送る機能は次の段で実装します
（手順は [docs/PLAN-request-mail.md](docs/PLAN-request-mail.md)）。

> **開発を再開するときは [docs/PROGRESS.md](docs/PROGRESS.md) を先に読むこと。**
> 現在地・手元で動かす手順・技術判断の理由・踏んだ罠・次にやることをまとめている。

---

## 使い方（月末の流れ）

1. **設定** — 初回のみ。銀行から取得した振込依頼人コード等を登録する
2. **取り込み** — Gmailで請求書メールの添付PDFをまとめてダウンロードし、画面にドラッグ&ドロップ
3. **請求書一覧** — 1件ずつ開き、PDFと読み取り結果を突き合わせて修正 → 「承認」または「今回は振り込まない」
4. **CSV出力** — 取組日を選び、検証エラーがなければCSVをダウンロード
5. ネットバンキングの ［資金移動 ≫ 振込ファイルによる新規作成］ でアップロード
6. 振込が終わったら出力履歴の「振込済みにする」を押す

### やり直したいとき

未処理・承認済み・除外の3つは、一覧でチェックを入れれば行き来できます（承認や除外の取り消し）。

CSV出力済み以降は状態を変更できません。銀行へ送ったデータと手元の記録がずれると二重振込に
つながるためです。取り込みからやり直したい場合は**削除**してください。
削除すると同じPDFを取り込み直せるようになり、口座情報は取引先マスタから補完されます。
**CSVの出力履歴と生成済みのCSVファイルは残る**ので、銀行へ何を送ったかの記録は失われません。

> 銀行で振込が完了しているものを削除して取り込み直すと、二重取込の防止（SHA-256の一意制約）が
> 効かなくなり、二重振込になる恐れがあります。削除前の確認ダイアログでも警告します。

## ローカルで動かす（デプロイ前の動作確認）

Google Cloud / Vercel Blob / Neon の登録なしで、この4ステップで一通り操作できます。
外部サービスを使う本番の経路はそのまま残してあり、環境変数で切り替えているだけです。

```bash
docker compose up -d          # ローカルPostgres（ホスト側ポート 55432）
cp .env.example .env          # 下記の3行を有効にする
npx prisma migrate dev        # テーブルを作成
npm run dev                   # http://localhost:3000
```

`.env` で有効にする行:

```
DATABASE_URL="postgresql://invoice:invoice@localhost:55432/invoice?schema=public"
AUTH_SECRET="..."             # node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"
ALLOWED_EMAILS="あなたのメールアドレス"
AUTH_DEV_LOGIN="1"            # メールアドレスだけでログインできる簡易ログイン
STORAGE="local"               # PDFを .uploads/ に保存する（Vercel Blob を使わない）
EXTRACTOR="stub"              # PDFを読まずダミーの読み取り結果を返す
```

`/signin` に「開発用ログイン」が出るので、`ALLOWED_EMAILS` に入れたアドレスでログインします。

| 変数 | 役割 | 本番との違い |
|---|---|---|
| `AUTH_DEV_LOGIN` | メールアドレスだけでログイン | **`NODE_ENV=production` では立てても無効**（`src/auth.ts` で二重にガード） |
| `STORAGE=local` | PDFを `.uploads/` に保存 | 本番はブラウザから Vercel Blob へ直接アップロード |
| `EXTRACTOR=stub` | ダミーの読み取り結果 | **本番で指定すると起動時に例外**。偽の口座がCSVに載るのを防ぐため |

`ANTHROPIC_API_KEY` を設定して `EXTRACTOR` の行を消すと、実際の請求書PDFで読み取り精度を確認できます。
読み取りは1通10〜40秒、費用は claude-opus-5 で**1通あたり数円**（月50件で150円程度）。

> **`EXTRACTOR="stub"` の間は、画面上部に赤帯が出て「読み取り結果はダミーです」と表示されます。**
> 明細画面にも「スタブ読み取り（PDF未読）」バッジが付きます。この状態の口座情報で振り込まないでください。

投入するPDFは `samples/` に置きます（**Git管理外**。実請求書をコミットしないため）。
手元に無ければ `node scripts/make-sample-pdfs.mjs` でダミーを3通作れますが、
口座情報が入っていないので `EXTRACTOR=stub` のときだけ意味があります。

`docker compose down -v` でDBを初期化できます。

### 1. 必要な外部サービス

| 環境変数 | 取得先 |
|---|---|

| `BLOB_READ_WRITE_TOKEN` | Vercel ダッシュボード → Storage → Blob ストアを作成 |
| `ANTHROPIC_API_KEY` | [Anthropic Console](https://console.anthropic.com) |

> `ALLOWED_EMAILS` が空の場合、**誰もログインできません**。
> 未設定のまま公開して全員が入れてしまう事故を防ぐための挙動です。

### 2. 起動

```bash
cp .env.example .env    # 値を埋める
npm install
npx prisma migrate dev  # DBにテーブルを作成
npm run dev
```

### 3. 銀行から取得しておく値（設定画面で入力）

ネットバンキングの ［資金移動 ≫ 振込データの新規作成］ 画面で確認できる。

- 振込依頼人コード（委託者コード）— 「20」ではじまる10桁
- 振込依頼人名 — 銀行に届け出ている名義
- 仕向支店番号（3桁）／依頼人口座番号（7桁）

## 設計上の要点

### 二重振込を防ぐ仕組み

金銭事故に直結するため、機能を削っても以下は落とさない。

| 仕組み | 実装場所 |
|---|---|
| 同一PDFの二重取込を弾く（SHA-256の一意制約） | [route.ts](src/app/api/invoices/route.ts) — ハッシュはクライアント申告を信用せずサーバーが実体から計算する |
| 人が承認するまでCSVに載らない | 取り込み直後は必ず `NEEDS_REVIEW` |
| 出力済みは再出力・編集できない | [actions.ts](src/app/actions.ts) / [export/route.ts](src/app/api/export/route.ts) |
| 1件でも検証エラーがあればCSVを生成しない | [csv.ts](src/lib/zengin/csv.ts) |
| 同一口座・同一金額の重複を警告 | [export.ts](src/lib/export.ts) |
| 取引先マスタと口座が違えば承認をブロック（口座変更詐欺対策） | [vendors.ts](src/lib/vendors.ts) / [actions.ts](src/app/actions.ts) |

### 金融機関コード・支店番号は読み取らない

**請求書に数字として印字されている場合だけ採用し、銀行名や支店名から補完しません**（`bankCode` / `branchCode` は null）。
LLMは「三井住友銀行なら0009」といった一般知識を持っているため放っておくと埋めてしまいますが、
その値は請求書のどこにも書かれていないので**人が突き合わせて検算できません**。
振込先を間違えると金銭事故になるため、確認できない値は入れない方針にしています。

そのため、コードが印字されていない請求書は**画面で人が入力するまでCSV出力がブロックされます**
（「被仕向銀行番号が未入力です」等）。銀行名・支店名は読み取って残すので、それを見て入力してください。
**この入力は取引先ごとに1回だけです**（下記「取引先マスタ」）。

### メール経由の取り込み（Gmail）

請求書受け取り専用のGmailアドレスを設定画面で**1回だけ接続**すると、以後は誰がログインしていても
「取り込み → メール経由」で期間を指定するだけで取り込めます。**権限は読み取りのみ**で、
ラベル付与も既読化もしません。取り込み済みの記録はすべてこのアプリのDBで持ちます。

**期間内のものは一度にすべて取り込みます。** 前回失敗した分も、もう一度ボタンを押せば自動で拾い直します。
何度実行しても二重には取り込まれません（同じ添付は一意制約で1行しか作られず、
同じ内容のPDFは既存のSHA-256の一意制約で弾かれます）。

#### 同じ請求書が2回届いたとき

再送・催促で同じPDFが届くのは毎月それなりに起きます。**重複分は取り込まず**、
元からある請求書の行に **「メールで再送 2回」** というバッジを請求書一覧に出します
（マウスを乗せると、いつ・誰から届いたかが出ます）。

本当に2件の請求だった場合も1件に見えますが、**バイト単位で同一のPDFを2件振り込むほうが遥かに危険**
なので安全側に倒しています。2件の請求なら、送信元に別々の請求書を出してもらってください。

#### 本文のリンクで届いた請求書

「請求書はこちら」のようにURLだけが書かれたメールも取り込みます。ただし
**本文中のURLを手当たり次第に開くことはしません。**

本文とリンク一覧をClaudeに渡して「請求書のダウンロードリンクはどれか」を判定させ、
**選ばれた1〜2本だけ**を実際に取得します。配信停止・退会・承認のリンクをシステムが勝手に押すと、
取り消せない結果が出るためです。迷ったときは「リンク無し」に倒します
（取りこぼしは人がGmailを見て拾えますが、押したリンクは取り消せません）。

取得した結果は次のように分かれます。

| 結果 | 扱い |
|---|---|
| PDFだった | 添付PDFとまったく同じ経路で取り込みます |
| ログイン画面だった | **「ログインが必要（依頼待ち）」**として残ります。「送付依頼」タブから取引先に依頼します（下記） |
| 請求書のリンクが無かった | 自動で除外し、件数だけ出します（広告・通知メールなど） |

判定は1通あたり数円かかります（本文のみを渡すので、PDFの読み取りより安く済みます）。

> **外部のサイトへ接続する処理なので、内部アドレスへ到達しないよう多重に防いでいます。**
> 名前解決した結果のIPを検査し、**検査を通したIPそのものに接続**します（解決してから接続するまでの
> 隙に別のIPへ向け直される攻撃を防ぐため）。リダイレクトも1ホップずつ検査し直し、
> プライベートアドレス・loopback・クラウドのメタデータ（169.254.169.254）には到達しません。
> 実際にローカルへサーバーを立てて、一度も到達しないことをテストで確認しています。

#### 「請求書をPDFで送ってください」の依頼メール（送付依頼タブ）

楽々明細のようなログインが要るサイトの請求書は自動で取得できないので、
**取引先に「請求書をPDFで添付して送ってください」と依頼するメール**を画面から送れます。

- **自動送信はしません。** 1件ずつ、宛先・件名・本文を画面で確認してから人が送ります
- **一括送信も作っていません。** 各社で宛名も元の件名も違ううえ、一括送信は
  「文面の書き間違いが全社に同時に届く」唯一の経路になるためです
- 文面は設定画面で編集できます（`{{取引先名}}` などを差し込めます）。
  **展開されていない `{{…}}` が残っていると送信ボタンは押せません**
- 本文には**金額・口座・URLを一切書きません**。誤送信しても漏れるのは取引先名と自社名だけです

既定では**元のメールへの返信**として送ります。取引先が請求書を添付して返信すると同じ
スレッドに戻るので、**「返信が来たか」を推測ではなくスレッドIDの一致で判定できる**ためです
（件名を書き換えると新規メールになり、その旨が画面に出ます）。

| 状態 | 画面での扱い |
|---|---|
| 依頼待ち | 「送付依頼」タブの未送信に出る。タブに件数バッジが出続ける |
| 送信済み・返信待ち | **決着にしません。** 7日で橙、14日で赤。返信が来て初めて決着します |
| 返信が届いた | 添付PDFは次の取り込みで請求書になり、依頼が決着します |
| 送信に失敗 | **自動で再送しません。** Gmailの「送信済み」を確認してから人が送り直します |

「依頼を送っただけ」で決着にしないのは、**依頼を無視された請求書が「済」の札を付けて
画面から消える**のを防ぐためです（それを見落とすのが、このシステムが防ごうとしている支払漏れそのものです）。

二重送信は4層で防いでいます: 状態の原子的な占有 / 送信APIを自動再試行しない
（502やタイムアウトは「Gmailが受理した後」にも起きるため）/ 同じ宛先への短期間の再送を警告 /
失敗を「押せば直る」状態にしない。

> **noreply宛の警告**: Web明細の通知は `noreply@` から届くことが多く、そのまま送っても届きません。
> 画面で警告を出すので、取引先の担当窓口のアドレスに変更してください（ブロックはしません）。

#### 抜け洩れを出さないための作り

月に一度の振込で1件でも請求書を見落とすと支払漏れになるため、
「たぶん全部拾えた」ではなく**拾えたことを画面で確認できる**ようにしています。

| 仕組み | 意味 |
|---|---|
| **添付が無いメールも1行ずつ記録する** | 行が無いと「添付が無かった」のか「見落とした」のか後から区別できない |
| **走査済みの期間を帯で可視化し、隙間を赤く出す** | 「前回どこまで見たか」を保存せず、完了した走査の記録から毎回導出する。保存するとずれ、ずれた分が抜け洩れになる |
| **完了は「ページングが尽きた」ときにしか立てない** | 途中で止まった走査は走査済みに数えない。隙間として残り続ける |
| **走査したメール件数を表示し、クエリをコピーできる** | Gmailの検索欄に同じクエリを貼って件数を突き合わせられる（推定値ではなく実際に数えた値） |

**PDF以外・パスワード付き・破損した添付は取り込まず、件数を表示します。**
Excelで届いた請求書やパスワード付きの請求書が「無かったこと」にならないためです。
件数が出たらGmailで該当メールを確認し、必要なら「アップロード経由」から入れてください。
自動で脇に寄せるのは、本文に埋め込まれた署名画像だけです（これも件数は表示します）。

期間の境界は、Gmailの検索に**前後1日多く引かせて**から、Gmailが記録した受信時刻
（`internalDate`）で絞り込みます。`after:`/`before:` はタイムゾーンの解釈がアカウント依存で
境界が曖昧なため、その曖昧さをマージンで吸収しています。
期間は半開区間なので、隣接する走査に重なりも隙間も生じません。

#### 取り込んだ請求書を削除したとき

**削除の確認画面で「次回の取り込みで、メールから拾い直す」を選べます**（既定は入っています）。

外して削除すると、その添付はメールから二度と取り込まれません。やり直したくなったら、
GmailからPDFを落として「アップロード経由」に入れてください。

再走査で勝手に復活させないのは、銀行へ振込済みのものを誤って削除した場合に、
気づかないうちに二重振込の対象として戻ってくるのを防ぐためです。

### Gmail取込の設定

**専用アドレスは必ず Google Workspace のドメイン内ユーザーとして作成してください**
（例 `invoice@自社ドメイン`）。`gmail.readonly` はGoogleの「制限付きスコープ」で、
Workspace組織の**内部(Internal)アプリなら審査不要**ですが、無料の `@gmail.com` だと
外部アプリ扱いになり、審査（年次・有償のセキュリティ評価）を通さない限り
**接続が7日ごとに切れます**。

1. 専用アドレスを Workspace のユーザーとして作成する
2. **Workspace組織が所有するGCPプロジェクトを新規作成**（Gmail連携専用。組織所有でないと Internal を選べない）
3. そのプロジェクトで **Gmail API を有効化**
4. Google Auth Platform → **Audience を「Internal」に設定**
5. Data access に次の2つを追加
   - `https://www.googleapis.com/auth/gmail.readonly`（取り込み。制限付きスコープ）
   - `https://www.googleapis.com/auth/gmail.send`（送付依頼メール。Sensitive なので審査区分は上がりません）
6. 認証情報 → OAuthクライアントID（**ウェブアプリケーション**）を作成。承認済みリダイレクトURIに2件:
   - `http://localhost:3000/api/gmail/callback`
   - `https://<本番ドメイン>/api/gmail/callback`
7. `.env` に `GMAIL_CLIENT_ID` / `GMAIL_CLIENT_SECRET` / `GMAIL_TOKEN_KEY` / `APP_BASE_URL` を設定
8. 設定画面の「Gmailを接続する」を押し、専用アドレスで認可する

> **ログイン用の `AUTH_GOOGLE_*` とは別のOAuthクライアント・別のGCPプロジェクトにしてください。**
> 「Internal」はクライアント単位ではなくプロジェクト単位の設定なので、ログイン用と共有すると、
> `ALLOWED_EMAILS` に組織外のアドレスを入れた瞬間にログインが壊れます。

リフレッシュトークンは **AES-256-GCM で暗号化して**DBに保存します。鍵は環境変数（Vercel）、
暗号文はDB（Neon）に置くことで信頼境界を分け、片方だけが漏れても復号できないようにしています。

> **既に接続済みの環境で送付依頼メールを使うときは、設定画面の「接続し直す」を1回押してください。**
> トークンの更新はスコープを引数に取らないため、既存の接続は読み取り専用のまま動き続けます
> （＝取り込みは止まりませんが、送信だけができません）。設定画面に警告が出るので、
> 押し忘れて送信時の403で気づく、ということは起きません。

### 取引先マスタ

一度確認した振込先を「取引先」タブに登録しておくと、**次回以降の請求書で空欄の項目が自動で埋まります**。
明細画面で口座を埋めたあと「この内容で取引先を登録」を押すのが一番簡単な登録方法です。

補完の規則は次の2つだけです。

- **空欄の項目しか埋めません。** 請求書から読み取れた値をマスタで上書きすることはありません
- **食い違う項目は埋めません。** 代わりに警告します

補完だけが目的ではありません。取引先名で照合しているので、
**同じ取引先なのに口座が違う請求書＝口座変更詐欺の形**を検知できます。
請求書一覧の「取引先マスタ」列に状態が出ます。

| 表示 | 意味 | 承認 |
|---|---|---|
| **一致** | 取引先名・口座ともマスタと一致 | できる |
| **口座相違** | 取引先名は一致するが**口座が違う** | **できない** |
| **名称相違** | 口座は一致するが取引先名が違う（改称・表記変更） | できる |
| **新規** | マスタに該当なし。登録すれば次回から補完される | できる |

口座相違のときは、取引先へ電話などで確認したうえで、明細画面で
「マスタを更新する」（正当な口座変更だった）か「今回はこの口座で振り込む」（今回だけ）を選ぶまで承認できません。
一括承認でも該当分だけが弾かれます。

取引先名は「株式会社サンプル」「サンプル(株)」「ｻﾝﾌﾟﾙ　株式会社」を同じ取引先として照合します。

### 全銀フォーマットの半角カナ変換

受取人名は**半角カタカナ・英大文字・数字・一部記号**しか使えない。
誤ると銀行で受付エラーか振込不着になるため、[kana.ts](src/lib/zengin/kana.ts) に切り出して単体テストで固めている。

- 濁点・半濁点は分離され**2文字を消費する**（`ガ` → `ｶ` + `ﾞ`）
- 小書き文字は大書きに（`キャノン` → `ｷﾔﾉﾝ`）
- 法人格は位置で表記が変わる（前株 `ｶ)ｻﾝﾌﾟﾙ` / 後株 `ｻﾝﾌﾟﾙ(ｶ` / 中間 `(ｶ)`）
- **カンマと円記号は意図的に使用不可**にしている
  — カンマはCSVの区切りと衝突し、円記号はShift_JISで `0x5C` と曖昧なため
- 漢字が残るなど変換できない文字があれば `ok: false` を返し、**CSV出力をブロックする**

### CSVフォーマット

[仕様書PDF](https://www.netbk.co.jp/contents/resources/pdf/doc_soufuri_furikomicsv.pdf) に準拠。
Shift_JIS・CRLF・全項目半角。ヘッダー(1) → データ(2)×n → トレーラ(8) → エンド(9)。

仕様書に載っている出力例と**バイト単位で一致する**ゴールデンテストを
[csv.test.ts](src/lib/zengin/csv.test.ts) に置いている。フォーマットを触ったらここが壊れる。

### MVPで対応していないもの

- **Gmail自動取り込み** — 手動でダウンロードしてドラッグ&ドロップする
- **URL型の請求書** — サービス側でログインが必要なため自動取得できない。人がDLして投入する
- ~~取引先マスタ・口座変更の検知~~ — **実装済み**（上記「取引先マスタ」）
- **ゆうちょ銀行** — 「記号-番号」は振込用の店番・口座番号への変換が必要。
  読み取り時に検出してメモに残すが、変換はしない。当面は手動振込に回す
- **監査ログ** — 最終更新者のみ記録している

## 開発

```bash
npm run dev        # 開発サーバー
npm test           # 単体テスト90件（半角カナ変換・CSV生成・営業日判定・取引先照合）
npm run typecheck  # 型チェック
```

### 本番稼働前に必ず通すゲート

1. 生成したCSVをネットバンキングにアップロードし、
   **受付内容確認画面で件数・合計金額・受取人名が正しく表示されるところまで確認**（確定せずに破棄）
2. 自社の別口座宛に **1円×2件で実振込を1回**実行し、着金と受取人名の表示を確認
3. 初月は従来の手作業と並行し、振込リストを目視で突き合わせる
