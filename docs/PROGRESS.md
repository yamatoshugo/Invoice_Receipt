### 第2段前半 — 本文リンクの取り込み（2026-09-14）

「PDFとURLで届く請求書を自動で取り込む」の**URL側の前半**。本文のリンクを判定し、
**PDFに直接つながるものは取り込む**ところまで。要ログインのポータルは
`LOGIN_REQUIRED` として残し、依頼メールの送信は次の段（[PLAN-request-mail.md](PLAN-request-mail.md)）。

#### 設計の中心 — LINK候補は「メール1通につき1行」

第1段のスキーマコメントには「LINK なら正規化したURLを `ref` に入れる」と書いたが、**変更した**。
URLごとに行を作ると、**配信停止リンクにも `PENDING` の行ができ、取り込みループが実際に叩きに行く**。
「絶対に踏まない」という要件と正面から衝突する。
→ `kind = LINK` の行は `ref = "body"` 固定。実際に取得を試みたURLは `url` 列に残す。

#### 本文中の全URLを叩かない

本文とリンク一覧をClaudeに渡して請求書のリンクを1〜2本に絞り、**選ばれたものだけ**を取得する。
プロンプトで「配信停止・退会・承認のリンクを選ばない」「迷ったら none」を明示している
（`src/lib/linkpick/claude.ts`）。**URLは文字列ではなく一覧の番号で返させる** —
署名付きURLを1文字書き換えられると取得が壊れ、存在しないホストを作られると外部への接続要求になるため。

#### 取得は SSRF 対策が要点

**名前解決した結果のIPを検査し、検査を通したIPそのものに接続する**（`node:https` の `lookup` を差し込む）。
先に `dns.lookup` してから `fetch` すると、その隙に別のIPへ解決し直される（DNSリバインディング）。

**実測で本物の漏れを1件見つけた**: ホストがIPリテラル（`http://127.0.0.1/`）の場合、
Node は名前解決を行わないので `lookup` が一切呼ばれず、素通しになっていた。
`blockedHostReason` でIPリテラルを検査するよう修正済み。
`src/lib/safefetch/fetch.test.ts` がローカルに番兵サーバーを立て、一度も到達しないことを確認している。

そのほか: リダイレクトは1ホップずつ追って毎回IPとスキームを検査 /
サイズ上限はストリームで数えて打ち切り（`Content-Length` は嘘のことがある）/
`accept-encoding: identity` で圧縮を断る（解凍爆弾でサイズ上限が意味を失うのを防ぐ）。

**判定に迷ったら `NOT_PDF` に倒す。** `LOGIN_REQUIRED` は（次の段で）取引先へメールが飛ぶ状態で、
**送ったメールは取り消せない**。誤検知の代償が非対称なので、証拠が無いときはメールを出さない側にする。

#### iconv-lite が ISO-2022-JP に対応していない

日本語メールの定番なのに、iconv-lite はステートフルな符号化を扱わない方針で非対応。
依存を増やさず、**JIS X 0208 の2バイトは各バイトに 0x80 を立てると EUC-JP になる**関係を使って
変換してから iconv-lite に渡している（`src/lib/gmail/charset.ts`）。
これが無いと本文が文字化けし、LLMの判定精度が落ちる。

#### 「分類し忘れれば必ず落ちる」を本当にした

第1段で「`Object.values(GmailItemStatus)` を回すテストがあるので、状態を足して分類し忘れれば落ちる」と
書いていたが、**`settlementOf` の末尾がフォールスルーだったので実際には落ちなかった**（黙って未決着になるだけ）。
`STATUS_CLASSIFICATION` という `Record<GmailItemStatus, ...>` の表にしたので、
**メンバーを足すと型エラーで止まり、表を回すテストでも落ちる**。

#### あわせて直したもの

- `/api/gmail/pending` が `kind` で絞っておらず、LINK行が添付取り込みループに流れ込む状態だった
- 失敗の自動再試行に上限（5回）を付けた。消えたURLを毎回叩き直さないため。
  上限に達しても `FAILED` のまま未決着として画面に残る（静かに消えない）

### 第2段後半 — PDF送付の依頼メール（2026-09-15）

計画書 [PLAN-request-mail.md](PLAN-request-mail.md) の手順どおりに実装した。**計画からの変更点は2つだけ**（下記）。
ログインが要るポータルだった請求書について、取引先へ「PDFで送ってください」と依頼するメールを
**画面で1件ずつ確認してから人が送る**。

#### 依頼者に1回だけお願いすること

**設定画面の「接続し直す」を1回押してもらう。** `gmail.send` を要求スコープに足したが、
トークンの更新はスコープを引数に取らないので、**既存の接続は読み取り専用のまま有効**。
つまり「読めるが送れない」状態になる。これを送信時の403で気付くのではなく、
`sendCapability()` がDBの `scope` だけで事前に判定し、設定画面と依頼画面に警告を出す。
**押すまで取り込みは普通に動く**（止めない）。

#### 計画から変えたところ

1. **接続を保存した直後に、そのトークンで実際にアクセストークンを取れるか試す**
   （`connection.ts` の `verifyRefreshToken`）。計画では「古いトークンを revoke する」だけだったが、
   Googleの revoke が同じ grant の新しいトークンまで巻き込む可能性をゼロとは言い切れない。
   巻き込まれた場合、**次の取り込みまで壊れたことに気付けない**ので、
   保存 → 古い方を revoke → 新しい方を検証、の順にした。失敗したら行に理由を書いて
   設定画面が「連携が切れています」を出す。
2. **返信待ちの一覧に「もう一度送る」を置かなかった。** 計画の画面案にはあったが、
   二重送信対策の1層目（状態の原子的占有）は `REQUEST_SENT` を意図的に対象外にしてある。
   ボタンを置くと「押しても何も起きない」か、占有を緩めるかのどちらかになる。
   催促は「Gmailで開く」から人が直接やる形にした（催促の自動送信を作らない方針とも揃う）。

#### 実装で効いている判断

- **`REQUEST_SENT` は単体では決着にしない。** `ItemLike.repliedAt` を**必須フィールド**にしたので、
  返信状況を渡し忘れた画面は型エラーで止まる。決着はDBに持たず、毎回導出する方針のまま
  （`requests.ts` の `attachReplies` が計算して渡す）
- **自分の送信控えを返信と数えない。** 走査クエリ(`buildGmailQuery`)は送信済みを除外していないので、
  依頼メールは次の走査で必ず `GmailMessage` として記録される。弾かないと
  **送った瞬間に「返信が来た」ことになり、返信待ちの検出が丸ごと死ぬ**。
  走査クエリは触らず（走査済み期間の意味が変わる）、`reply.ts` で From と SENT ラベルの両方で弾く
- **件名のRFC2047は base64 の前・コードポイント境界で切る。** base64にしてから長さで切ると
  マルチバイト文字が2つのエンコード語にまたがって必ず壊れる。`for...of` で回すのは
  サロゲートペア（𠮷・絵文字）を半分に割らないため。検証は**受信側で既に使っている
  `decodeMimeFilename` との往復**で行うので、テストが実装の写しにならない
- **ヘッダインジェクション。** 日本語の件名はbase64に飲まれて無害化されるが、
  **純ASCIIの件名は素通しになる**ので `sanitizeHeaderValue` でCR/LFを落とす。
  In-Reply-To / References も取引先のメール由来の外部入力なので同じ扱い
- **送信APIは自動再試行しない**（`maxRetryAttempts: 1`）。502やタイムアウトは
  「Gmailが受理した後」にも起こるため。401だけは別で、Gmailに届く前の拒否なので1度だけやり直す
- **差し込みの置換は文字列でなく関数で行う。** 文字列だと取引先名に含まれる `$&` `$1` が
  パターンとして解釈されて本文が壊れる（取引先名は請求書から来る外部の値）

#### 実送信で見つけて直した不具合（2026-09-15）— 全角スペースが潰れていた

**自分宛に1通送って初めて分かった。** 元の件名「請求書受け取りアプリ**　**テストメール」の
**全角スペース(U+3000)が半角スペースに変わって**届いていた。

原因は `sanitizeHeaderValue` の `.replace(/\s+/g, " ")`。**JavaScriptの `\s` は U+3000 にもマッチする。**
畳んでよいのはASCIIの空白だけなので `[ \t]+` に直した（`trim()` も同じ理由で使わない）。

**見た目の問題ではない。** 件名が1文字でも変わるとGmailは元のスレッドに入れてくれず、
そうなると**取引先の返信が別スレッドに落ちて、返信の検出（`reply.ts`）が拠って立つ仕組みごと崩れる**。
純関数のテストは全部通っていたので、実際に送るまで見つけられなかった類の不具合。
回帰テストを `rfc2822.test.ts` に追加済み。

## 1. このプロジェクトは何か

月に約50件届く請求書を手入力で振込処理している状態を解消する。
請求書PDFを取り込んで振込情報を自動で読み取り、画面で確認・承認したうえで、
**ドコモSMTBネット銀行の総合振込CSV（Shift_JIS）** を出力する。

出力したCSVをネットバンキングにアップロードするだけで月末の一括振込が終わる、という状態がゴール。

計画書の原本: `C:\Users\yamato\.claude\plans\csv-4-50-pdf-url-smtb-csv-pc-wbs-cryptic-haven.md`

#### 実際に使ってみて直したこと（2026-09-14 夕）

依頼者が実メールで取り込んだうえで出た指摘。**すべて実使用から出たものなので、そのまま直した。**

1. **「走査していない期間があります 2026-09-14 〜 2026-09-14」が出る** — 表示バグ。
   走査の上限は常に「今より10分前」で止めているのに、帯の右端を「今」にしていたため
   **10分ぶんの隙間が永久に残っていた**。帯の右端を走査済みの右端にして、
   直近の未走査分は隙間ではなく「〜まで走査済み」という文言にした。
   残る隙間は「走査済み期間の内側にある本物の穴」だけになる。
2. **「過去の走査」「添付の一覧」を削除** — 月1回の作業に対して管理UIが重すぎた。
   結果は件数だけを出す形に整理した。
   これに伴い、個別の確認・再試行のServer Actionも削除
   （`acknowledgeGmailItem` / `unacknowledgeGmailItem` / `retryGmailItems` / `reopenGmailItem`）。
3. **期間内のものは一度にすべて取り込む** — 一覧が無くなると失敗分を再試行する導線も無くなるので、
   `/api/gmail/pending` が `FAILED` も返すようにした。もう一度ボタンを押せば自動で拾い直す。
4. **タブを5つに戻し、取り込みの中にサブタブを作った** — `/gmail` は廃止。
   `/upload`（メール経由）と `/upload/file`（アップロード経由）。入口が2つトップに並んで
   どちらを使うのか分かりにくい、という指摘。

あわせて決めたこと:

- **重複は請求書一覧に出す。** 同じPDFが再送されたら、元の請求書の行に「メールで再送 N回」バッジ。
  重複分の請求書は作らない（SHA-256の一意制約＝二重振込の砦は外さない）。
  「同じ請求書が2回来た」は請求書そのものの事実なので、月末に目が行く請求書一覧に出すのが自然。
- **PDF以外・開けなかった添付は件数だけ出す**（依頼者の選択）。どのメールかは画面から分からない。
  **DBの行(`GmailItem`)は全件残してある**ので、詳細を出したくなればクエリ1本で戻せる。
- **削除時に「メールから拾い直す」を聞く。** 添付の一覧を消すと再取り込みの導線が無くなるため、
  判断する場面（削除する瞬間）で聞く形にした。既定は「拾い直す」。
  チェックを外すと `acknowledgedAt` が立ち、未処理として残り続けない。
  `GmailItem.invoiceId` は `onDelete: SetNull` なので、**削除する前に紐づく候補を引いておくこと**。
  削除は `window.confirm` ではチェックボックスを置けないため、インラインの確認パネルにした。

#### 第2段を後から載せるために、今やっておいたこと

ここが今回の設計で一番効く部分。**第2段でテーブルを作り直さずに済むようにしてある。**

1. **作業単位を「添付」ではなく `GmailItem`（取り込み候補）＋ `kind` 判別子にした。**
   抜け洩れゼロを支える機構（決着判定・未決着バナー・突合サマリ・一覧・再試行）は
   添付でもURLでも完全に同じものが要る。添付専用に作ると第2段で全部書き直しになる。
   今回作られる行は `kind = ATTACHMENT` だけ。第2段は `LINK` を足し、
   「候補を作る関数」と「PDFを手に入れるまで」を1つずつ書けば済む。
2. **`GmailMessage.attachmentsScannedAt` を持たせた。**
   メールの決着は「有効な調べ方をすべて終えたか」で判定する。
   第2段で `linksScannedAt` を足した瞬間、**既存の全メールが自動的に未走査になり、
   過去に遡る特別な作業なしに第2段の処理対象として画面に出る。**
   これが無いと、第2段のリリース時に「いつからいつまで調べ直すか」を人が考えることになり、
   そこが抜け洩れの入口になる。
3. ~~**`gmail.send` はまだ取っていない。**~~ **2026-09-15に追加済み**（`oauth.ts` の `GMAIL_SCOPES`）。
   専用アドレスがWorkspaceドメイン内なので、スコープを増やしてもGoogleの審査は発生しなかった。
   **既存の接続は readonly のままなので、繋ぎ直すまで取り込みは動き続け、送信だけができない。**
   依頼者が設定画面の「接続し直す」を1回押すのが残作業（10秒・1回きり）。

宛先も既に揃っている（`GmailMessage.fromAddress` を今回から保存している）。

### 踏んだ罠と対処（同じ轍を踏まないこと）

1. **Prisma 7系は `datasource.url` がスキーマから廃止**され、`prisma.config.ts` とドライバアダプタが必須になる。設定が増えるので**6系に戻した**。
2. **`npm view prisma version` は 8.0.0-rc を返す**（`latest` タグがRCを指している）。`@prisma/client` の安定版は7系。バージョンを調べるときは `dist-tags` を確認すること。
3. **Prismaの既定の生成先だとNext.jsのビルドが落ちる。**
   `node_modules/.prisma/client/default.js` が subpath import `#main-entry-point` を要求し、Next.jsの外部モジュールローダーがこれを解決できない。
   → `generator client { output = "../src/generated/prisma" }` にして、アプリのソース配下へ生成しバンドルさせることで解決。
   **`@prisma/client` からではなく `@/generated/prisma` から型をimportすること。**
   `next.config.ts` の `serverExternalPackages` も外してある（付けると再発する）。
4. **Vercelのリクエストボディ上限は4.5MB。** PDFをサーバー経由で送ると引っかかるため、
   ブラウザから Vercel Blob へ直接アップロードする方式にしている（`@vercel/blob/client` の `upload()`）。
5. `next dev` が **`AGENTS.md` / `CLAUDE.md` を自動生成する**。消してもまた作られるので、そのままコミットしてよい。
6. **Next 16 で `middleware.ts` は非推奨**（`proxy.ts` に改名、named export も `proxy`）。改名済み。
   公式ドキュメントの注意通り、Server Action は使用先ページへのPOSTとして扱われ matcher の除外がそのまま効くため、
   `proxy.ts` だけに頼らず `actions.ts` の `requireEmail()` で毎回セッションを検証している。
7. **`next dev` 起動中は `npm run build` が EPERM で落ちる。**
   Prismaのクエリエンジン(`src/generated/prisma/query_engine-windows.dll.node`)を掴んでいるため。
   ビルド前に開発サーバーを止めること。

### ローカル用の差し替えと、本番に漏らさないための仕掛け

デプロイ前に手元で操作を確認できるよう、外部サービス依存の3箇所を環境変数で差し替えられるようにしてある。
**どれも本番で誤って有効にならないよう、二重にガードしている。**

| 変数 | 差し替える対象 | ガード |
|---|---|---|
| `AUTH_DEV_LOGIN=1` | Google OAuth → メールだけの簡易ログイン | `NODE_ENV !== "production"` との**AND**。本番ビルドではプロバイダ自体が生成されない |
| `STORAGE=local` | Vercel Blob → `.uploads/` | 明示的に `"local"` と書いたときだけ切り替わる（既定は Vercel Blob） |
| `EXTRACTOR=stub` | Claude → ダミー値 | **本番で指定されたら例外を投げて止める**。偽の口座番号が振込CSVに載るのは金銭事故そのものなので、黙って通さない |

### 落としてはいけない安全策（実装済み）

| 仕組み | 場所 |
|---|---|
| 同一PDFの二重取込を弾く（SHA-256一意制約）。**ハッシュはクライアント申告を信用せずサーバーが実体から計算** | `api/invoices/route.ts` |
| 人が承認するまでCSVに載らない（取込直後は必ず `NEEDS_REVIEW`） | 全体 |

### 意図的な判断（レビュー時に「バグでは？」と思われそうな箇所）

- **カンマと円記号を全銀の使用可能文字から外している。**
  仕様書上は許容されるが、カンマはCSVの区切りと衝突し（引用符の規定がない）、
  円記号はShift_JISで `0x5C` がバックスラッシュと同一で曖昧なため。受取人名に含まれれば出力をブロックする。
- **銀行番号・支店番号・口座番号の先頭0を加工しない。** 仕様書が「先頭の0は省略可」としており、
  どちらでも受理される。呼び出し側から渡された数字をそのまま出す方が事故が少ない。
- **漢字が残る受取人名は変換せずエラーにする。** 読み方を機械的に決められないため、
  推測で埋めるより人にカナ入力させる方が安全。

- **金融機関コード・支店番号は、請求書に印字されている場合しか採用しない**（プロンプト v2 で明文化）。
  v1 では「三井住友銀行 → 0009」のように **LLMが一般知識から補完し、しかも確信度0.85〜0.9** を返していた。
  0009 自体は正しいが、その数字は請求書のどこにも印字されていないため**人が突き合わせて検算できない**。
  確信度が警告しきい値(0.8)を超えていたので画面に警告も出ず、「読み取れた値」に見えていた。
  → コードは null にして名称だけ残し、人に入力させる。併せて
  「請求書に印字されていない値を入れた場合は確信度を0.5以下にする」ルールも追加した。

  **代償**: コードが印字されていない請求書は、人が入力するまでCSV出力がブロックされる。
  実際に試した3通はいずれも支店名のみで店番の印字が無く、全件で入力が必要だった。
  → **取引先マスタで解消済み**（下記）。入力は取引先ごとに1回で済む。

- **取引先マスタの照合キーは「取引先名 → 銀行名＋口座番号」の2段にした。**
  口座番号だけで照合すると確実にマッチするが、**口座が変わった請求書は「マスタに無い」となるだけで
  警告を出せない**。口座変更詐欺は「同じ取引先なのに口座が違う」という形で来るため、
  先に取引先名で引く必要がある。名前が変わった取引先は口座番号で拾って「名称相違」にする。

- **照合状態はDBに保存せず、画面を出すたびに導出する。**
  保存すると、請求書を直したときやマスタを更新したときに実態とずれ、更新経路すべてで
  再計算が要る（必ずどこかで漏れる）。一覧はもともと全件を読むので、そこにマスタ全件を
  足して突き合わせるだけで済む。保存するのは「取り込み時に実際に何を補完したか」
  （`vendorFilledFields`）という履歴だけ。

- **口座相違は承認をブロックするが、除外はブロックしない。**
  止めたいのは「気づかないまま振り込むこと」だけで、「今回は振り込まない」判断は妨げない。
  名称相違（改称・表記変更が主因）も止めない。

- **CSV出力済みは状態を戻せないが、削除はできる。**
  出力済みの状態を未処理へ戻せるようにすると、銀行へ送ったデータと手元の記録がずれる。
  一方で「CSVを作ったが銀行にアップロードしなかった」ケースで永久に動かせないのは実務上つらい。
  そこで**状態変更は禁じたまま、削除だけを許す**形にした。
  削除すれば sha256 の行が消えるので同じPDFを取り込み直せる（取り込み直しは取引先マスタから補完される）。
  **`ExportBatch` は消さない**ので、銀行へ何を送ったか（件数・合計・CSVの実体）は残る。
  代わりに二重取込の防止が効かなくなるため、確認ダイアログで二重振込の恐れを明示している。

- **Gmail取込: 走査した期間の全メールを、添付が無いものも含めて1行ずつ残す。**
  行が無いと「添付が無かった」のか「見落とした」のかが後から区別できない。
  容量は月50〜100行程度なので、突合の解像度と引き換えにする価値がある。
  （添付が無いメールこそ、第2段でURL請求書の候補になる）

- **走査済みの期間を保存せず、完了した走査の記録から毎回導出する。**
  「前回どこまで見たか」をポインタで持つと必ずどこかでずれ、**ずれた分がそのまま抜け洩れになる**。
  照合状態をDBに持たないのと同じ理由。`coverage.ts` の純関数が結合と隙間の検出をやる。

- **完了は「`nextPageToken` が尽きた」ときにしか立てない。** 推測で完了にしない。
  中断した走査は `RUNNING` のまま残り、走査済み期間の帯に隙間として出続ける。
  カーソルは必ず**行を書き終えたあと**に進めるので、落ちてもカーソルが行より先に行かない。

- **期間の境界は、Gmailに1日多く引かせてから `internalDate` で絞る。**
  `after:`/`before:` は日付形式だとアカウントのタイムゾーン依存で境界が曖昧になり、
  epoch秒でも境界を含むかが明文化されていない。**マージンで曖昧さを丸ごと吸収する**。
  期間は半開区間 `[from, to)` なので、隣接する走査に重なりも隙間も原理的に生じない。

- **PDF以外・パスワード付き・破損を、自動で「済」にしない。**
  Excelで届いた請求書やパスワード付きPDFが黙って消えるのが、この機能で最も起きやすい抜け洩れ。
  人が「取り込まない」と確認するまで要対応として残る。
  自動で脇に寄せるのは、本文に埋め込まれた署名画像だけ（件数は必ず表示する）。

- **`resultSizeEstimate` を件数に使わない。** 「推定値」と明記されているので、
  これで一致を主張したら嘘になる。ページングで実際に数えたID数だけを出す。
  Gmailの画面はスレッド単位で数えるので、**メッセージ件数とスレッド件数を両方出す**
  （片方だけだと「412と356が合わない」と言われて信用を失う）。

- **Gmail取込で請求書を削除しても、候補の行は消さない（`onDelete: SetNull`）。**
  Cascade にすると行ごと消えて、再走査で黙って取り込み直される。
  SetNull なら `status = IMPORTED` かつ `invoiceId = null` になり、**未決着に戻って画面に赤く出る**。
  「再取り込み」を人が押したときだけ戻る。銀行へ振込済みのものを誤って削除した場合に、
  気づかないうちに二重振込の対象として復活するのを防ぐため（依頼者の決定）。

- **Gmail用のOAuthクライアントとGCPプロジェクトを、ログイン用と分けた。**
  `gmail.readonly` は制限付きスコープで、外部公開アプリなら審査＋CASA評価が要る。
  **Workspace組織の「内部(Internal)」アプリなら審査不要**だが、
  **Internal はクライアント単位ではなくGCPプロジェクト単位の設定**なので、共有すると
  `ALLOWED_EMAILS` に組織外のアドレスを入れた瞬間にログインが壊れる。
  この二律背反はプロジェクトを分ける以外に解けない。爆発半径の分離という副次効果もある。

- **refresh_token は AES-256-GCM で暗号化して保存する。鍵は `AUTH_SECRET` と別。**
  これは「請求書メールボックス全体を読める鍵」で、他のどの列より影響範囲が広い。
  鍵は環境変数(Vercel)、暗号文はDB(Neon)に置いて**信頼境界を分ける**。
  `AUTH_SECRET` から導出しないのは、そのローテーション（＝全員ログアウトするだけの安全な操作）に
  「Gmail連携が無言で壊れる」副作用を隠すのが危険だから。

- **`googleapis` を入れず `fetch` 直叩きにした。** 使うのは4エンドポイントだけで、
  ページングは `nextPageToken` を回すだけ。Prismaの subpath import でビルドが落ちた前例（§3 罠3）があり、
  動的requireの多い巨大パッケージで同じ問題を踏む理由がない。口座情報を扱う以上、依存は増やさない。

- **依頼メールを送っただけでは決着にしない（`REQUEST_SENT`）。** 返信が届いて初めて決着する。
  「返信が来れば別のメールとして取り込まれるから決着でよい」は順路しか見ていない定義で、
  そうすると**依頼を無視された請求書が「済」の札を付けて画面から消える**。
  決着は逆路（返信が来たか）で定義する必要がある。

- **添付の無い返信は決着にしない。** 「承知しました」だけの返信では請求書は手元に来ていない。
  画面には別表示で出し、人が「待たない」で閉じられるようにしている。

- **返信待ちの一覧に「もう一度送る」を置いていない。** 二重送信対策の1層目（状態の原子的占有）が
  `REQUEST_SENT` を対象外にしているため、置いても押せないか、占有を緩めるかになる。
  催促は「Gmailで開く」から人が直接行う（催促の自動送信を作らない方針とも揃う）。

- **依頼メールの送信だけは自動再試行しない。** 走査・取り込みは429/5xxで5回まで再試行するが、
  送信は1回きり。**502やタイムアウトは「Gmailが受理した後」にも起こる**ので、
  再試行すると同じ依頼が取引先に複数回届く。401だけは例外（Gmailに届く前の拒否なので1度やり直す）。

- **noreply宛でもブロックしない。** 警告を出して宛先を差し替えられるようにするだけ。
  ブロックすると、正しい窓口を知っている人が依頼を出せなくなる。

- **マスタの値で請求書を上書きしない。** 空欄の項目だけを埋める。
  上書きすると、検知したい「口座が変わっている」という事実がマスタの値で塗り潰される。

## 7. 全銀CSVフォーマット（実装の確定仕様）

Shift_JIS / カンマ区切り / CRLF / 全項目半角。
構成: ヘッダー(1) → データ(2)×n → トレーラ(8) → エンド(9)。「*」項目は省略可。

**ヘッダー**: `1`, `21`(総合振込), `0`, 振込依頼人コード(10), 依頼人名(カナ40), 取組日(MMDD/営業日),
仕向銀行番号(0038), *銀行名, 仕向支店番号(3), *支店名, `1`(預金種目固定), 依頼人口座番号(7)

**データ**: `2`, 被仕向銀行番号(4), *銀行名, 被仕向支店番号(3), *支店名, *手形交換所番号,
預金種目(1普通/2当座/4貯蓄/9その他), 口座番号(7), 受取人名(半角カナ30), 振込金額, *新規コード…

**トレーラ**: `8`, 件数, 合計金額 ／ **エンド**: `9`
